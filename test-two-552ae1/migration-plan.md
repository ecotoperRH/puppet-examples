# MIGRATION FROM PUPPET TO ANSIBLE

## Executive Summary

This repository is a Puppet 7/8 control repository implementing a **roles-and-profiles** pattern for three production workloads: a Python application stack (FastAPI/Gunicorn + PostgreSQL), an HAProxy load balancer, and a Redis cluster. It also contains a shared base utilities module used by all roles.

The migration involves **7 distinct Puppet modules** (4 in `modules/`, 3 in `site/modules/`) plus a thin roles-and-profiles wrapper layer in `site/`. The codebase is well-structured and internally consistent, which reduces migration risk. However, several Puppet-specific patterns — deep Hiera hierarchies, PuppetDB live node discovery, exported resources, virtual resources, custom Facter facts, and eyaml-encrypted secrets — require deliberate design decisions before Ansible equivalents can be written.

**Estimated migration complexity:** Medium-High  
**Estimated timeline:** 8–12 weeks for a small platform team (2–3 engineers), including testing and parallel-run validation.

---

## Module Migration Plan

This repository contains Puppet modules that need individual migration planning. The module path (from `environment.conf`) is:

```
site/modules/linux : site/modules/common : site : modules : $basemodulepath
```

Modules in `site/modules/linux/` shadow identically-named modules in `modules/` — the `linux/` variants are the authoritative versions for Linux targets and contain additional manifests (e.g., `discover.pp` in `profile_haproxy`). Both sets are documented below.

- **profile_app_stack** *(authoritative: `site/modules/linux/`)*
  - **Description:** Full Python application stack deploying a FastAPI/Gunicorn application from a Git repository onto Ubuntu. Manages the complete lifecycle: Python runtime and virtualenv setup, PostgreSQL database provisioning (local or remote), application deployment via `git clone` + `pip install`, systemd service unit generation, Alembic database migrations, log rotation, and Prometheus monitoring (production-only via virtual resources). A custom Puppet function (`app_db_url`) assembles the `DATABASE_URL` from individual Hiera parameters.
  - **Path:** `site/modules/linux/profile_app_stack` (shadows `modules/profile_app_stack`)
  - **Technology:** Puppet
  - **Key Features:** `vcsrepo` git deployment, Python virtualenv management, EPP/ERB templated `.env` file with environment-conditional `DEBUG`/`CORS` settings, systemd unit via EPP template, Alembic migration exec with `refreshonly`, Prometheus node-exporter and pushgateway (virtual resources realized only in production), logrotate config, nightly DB backup cron at 02:30, healthcheck script deployment, eyaml-encrypted `db_password` and `secret_key`

- **profile_haproxy** *(authoritative: `site/modules/linux/`)*
  - **Description:** HAProxy 2.x load balancer profile with a deep, multi-level Hiera hierarchy (node → cluster → datacenter → environment → OS → common — effectively 6+ levels within the module alone). Manages installation, a templated `haproxy.cfg`, per-backend config fragments generated by iterating a Hiera `backends` hash with deep merge, custom HTTP error pages (408, 503), UFW firewall rules, and dynamic backend discovery via PuppetDB exported resources. The `site/modules/linux/` variant adds a `discover.pp` subclass that uses PuppetDB queries and exported `haproxy::balancermember` resources to build the backend list dynamically at catalog compile time.
  - **Path:** `site/modules/linux/profile_haproxy` (shadows `modules/profile_haproxy`)
  - **Technology:** Puppet
  - **Key Features:** ERB `haproxy.cfg` template, EPP per-backend fragment loop, deep-merge `backends` hash across node/cluster/datacenter/environment layers, SSL termination (TLSv1.2 minimum, TLSv1.3 in production cluster), stats page with eyaml-encrypted password, UFW firewall management, stick-table session persistence (production only), custom Facter fact `haproxy_version`, PuppetDB-driven dynamic backend discovery with exported resources (`@@haproxy::balancermember` / `Haproxy::Balancermember <<| |>>`)

### Infrastructure Files

- `Puppetfile`: Declares all Forge module dependencies pinned to exact versions — `puppetlabs-stdlib 9.7.0`, `puppetlabs-concat 9.0.2`, `puppetlabs-firewall 8.1.3`, `puppetlabs-vcsrepo 6.1.0`, `puppet-redis 11.0.0`, `puppetlabs-apt 9.4.0`. These map directly to Ansible collection/role equivalents.
- `environment.conf`: Defines the four-segment module path (`site/modules/linux:site/modules/common:site:modules`). Establishes the module resolution order and the shadowing relationship between `site/modules/linux/` and `modules/`.
- `hiera.yaml` (root): Defines a 3-level global Hiera hierarchy: per-node (eyaml-encrypted), per-environment, and common. Uses PKCS7 eyaml for node-level secrets at `/etc/puppetlabs/puppet/eyaml/`.
- `data/common.yaml`: Global defaults for NTP servers, SSH hardening (`PermitRootLogin no`, `ClientAliveInterval 300`), and syslog target.
- `data/environment/production.yaml`: Production overrides — internal NTP servers (`ntp1/2.prod.internal`), production syslog endpoint.
- `data/environment/staging.yaml`: Staging overrides — staging syslog endpoint.
- `Vagrantfile`: Local development environment using `bento/ubuntu-24.04` on libvirt (2 vCPU, 2 GB RAM). Provisions via `vagrant-provision.sh`, forwarding ports 80→8080 and 443→8443.
- `vagrant-provision.sh`: Bootstraps Puppet 8 agent on Ubuntu Noble, installs all Forge modules, copies module tree, and runs `puppet apply` with `--detailed-exitcodes`. Also serves as the integration test runner.
- `test/Containerfile`: Container-based test fixture (complements Vagrant for CI).
- `test/site.pp`: Integration test manifest — creates a stub git repository with a FastAPI app, then applies all three profiles (`profile_haproxy`, `profile_app_stack`, `profile_redis_cluster`) on a single node.
- `test/hiera.yaml` / `test/data/common.yaml`: Minimal Hiera configuration for test runs, bypassing eyaml and node-level lookups.

## Migration Approach

### Key Dependencies to Address

- **puppetlabs-stdlib 9.7.0**: Provides `lookup()`, `file_line`, type aliases, and utility functions throughout all modules. Replace with native Ansible variable lookups (`vars`, `group_vars`, `host_vars`), `lineinfile`/`blockinfile` modules, and Jinja2 filters. No direct Ansible collection equivalent is needed.

- **puppetlabs-vcsrepo 6.1.0**: Used exclusively in `profile_app_stack` for `git clone` with revision pinning and ownership management. Replace with the `ansible.builtin.git` module, which supports `version`, `dest`, `owner`, and `group` parameters natively.

- **puppet-redis 11.0.0**: Wraps Redis installation and `redis.conf` generation. Replace with the `community.general` collection or a dedicated Redis Ansible role (e.g., `geerlingguy.redis`). The ERB `redis.conf` template maps cleanly to a Jinja2 template.

- **puppetlabs-concat 9.0.2**: Used in `profile_haproxy` to assemble per-backend config fragments. Replace with Ansible's `template` module iterating over a `backends` dictionary in a single Jinja2 template, or use `ansible.builtin.assemble` for fragment-based approaches.

- **puppetlabs-firewall 8.1.3**: Declared as a dependency but the actual firewall management in `profile_haproxy::firewall` uses raw `exec` calls to `ufw` rather than the `firewall` resource type. Replace with `community.general.ufw` module tasks.

- **puppetlabs-apt 9.4.0**: Used in Redis and HAProxy module Puppetfiles for APT repository management. Replace with `ansible.builtin.apt_repository` or `ansible.builtin.deb822_repository`.

- **eyaml (hiera-eyaml / PKCS7)**: Used for encrypting `db_password`, `secret_key`, and `stats_password` at rest in YAML data files. Replace with **Ansible Vault** (`ansible-vault encrypt_string` for inline secrets or vault files). The PKCS7 key pair at `/etc/puppetlabs/puppet/eyaml/` must be inventoried and all `ENC[PKCS7,...]` values decrypted and re-encrypted with Ansible Vault before cutover.

- **PuppetDB query function**: Used in both `profile_redis_cluster` and `profile_haproxy::discover` for live node discovery at catalog compile time. This has **no direct Ansible equivalent** — see Technical Challenges below.

- **Puppet Bolt tasks and plans** (`base_utils`): The `check_service` task and `health_check`/`rolling_restart` plans are operational automation tools. Replace with Ansible ad-hoc commands, `ansible.builtin.service` facts checks, and playbooks with `serial` + `max_fail_percentage` for rolling restarts.

### Security Considerations

- **eyaml-encrypted secrets (PKCS7)**: Three confirmed encrypted values across the reviewed data files:
  - `profile_app_stack::db_password` — PostgreSQL application user password (`data/common.yaml` and `modules/profile_app_stack/data/common.yaml`)
  - `profile_app_stack::secret_key` — Application `SECRET_KEY` for session signing (`modules/profile_app_stack/data/environment/production.yaml`)
  - `profile_haproxy::stats_password` — HAProxy stats page HTTP Basic Auth password (`modules/profile_haproxy/data/common.yaml`)
  
  All three must be decrypted using the PKCS7 private key at `/etc/puppetlabs/puppet/eyaml/private_key.pkcs7.pem` and re-encrypted with Ansible Vault. The private key itself must be securely transferred and then destroyed or archived.

- **Hardcoded default credentials**: `profile_redis_cluster` uses `redis_password: 'CHANGEME'` as the default parameter value in `init.pp`. This default is never overridden in any reviewed Hiera data file, meaning Redis nodes may be running with this insecure password. This must be resolved — either by injecting a proper secret via Ansible Vault or by confirming that a node-level Hiera override (not present in this repo) supplies the real value.

- **`.env` file with `SECRET_KEY` and `DATABASE_URL`**: The `app.env.erb` template writes `SECRET_KEY` and the full `DATABASE_URL` (including password) to `${app_dir}/.env` with mode `0600`. The Ansible equivalent must use `ansible.builtin.template` with `mode: '0600'` and source the values from Ansible Vault. The `no_log: true` directive should be applied to any task that handles these values.

- **HAProxy stats page credentials**: The stats page is enabled per-node (e.g., `lb01.fra.example.com`) with HTTP Basic Auth. The password is eyaml-encrypted in common data. In Ansible, use Vault-encrypted `host_vars` for node-specific stats credentials.

- **SSL/TLS certificate management**: `profile_haproxy` references `ssl_cert_path: /etc/ssl/certs` and `ssl_key_path: /etc/ssl/private` with a combined PEM at `/etc/ssl/certs/haproxy.pem`. No certificate provisioning logic exists in the Puppet code — certificates are assumed to be pre-placed. The Ansible migration must explicitly handle certificate deployment (e.g., via `ansible.builtin.copy` from Vault-encrypted files, or integration with a certificate management tool).

- **SSH hardening data**: `data/common.yaml` declares `ssh::permit_root_login: false` and `ssh::client_alive_interval: 300`, but no Puppet class consumes these keys in the reviewed code. These values should be implemented as explicit `ansible.builtin.lineinfile` or `ansible.posix.sshd` tasks in the base role.

- **Database password in `exec` commands**: `profile_app_stack::database` embeds `$db_password` directly in `psql -c "CREATE USER ... WITH PASSWORD '...'"` shell commands. These commands may appear in Puppet logs and process listings. The Ansible equivalent should use `community.postgresql.postgresql_user` with `password` parameter and `no_log: true`.

### Technical Challenges

- **PuppetDB live node discovery**: Both `profile_redis_cluster` and `profile_haproxy::discover` use `puppetdb_query()` to discover cluster members at catalog compile time. Ansible has no equivalent runtime service registry. **Mitigation:** Replace with static `group_vars` inventory for known cluster topologies, or integrate with a dynamic inventory plugin (e.g., `amazon.aws.aws_ec2`, `community.vmware.vmware_vm_inventory`, or a custom script querying a CMDB). For the Redis replica detection pattern, use Ansible facts gathered at play start combined with `when` conditionals.

- **Exported resources (`@@` / `<<| |>>`)**: `profile_haproxy::discover` uses Puppet's exported resource mechanism (`@@haproxy::balancermember` collected with `Haproxy::Balancermember <<| |>>`) to allow application nodes to self-register with the load balancer. This is a fundamentally catalog-server-side pattern. **Mitigation:** Replace with Ansible's `add_host` / `group_by` modules within a multi-play playbook, or use a shared state store (e.g., a Consul service registry or an inventory group populated by a prior play that runs on app nodes).

- **Deep Hiera hierarchy with deep-merge**: The `profile_haproxy` module uses a 6-level hierarchy within the module alone (node → cluster → datacenter → environment → OS → common), with `merge: deep` on the `backends` hash. This allows per-datacenter and per-cluster backend server lists to be composed automatically. **Mitigation:** Replicate with Ansible's `hash_behaviour=merge` (deprecated) or, preferably, use explicit `combine(recursive=True)` Jinja2 filter calls in the playbook, with `group_vars/` and `host_vars/` directories mirroring the Hiera hierarchy levels. This requires careful variable precedence design.

- **Virtual resources (production-only monitoring)**: `profile_app_stack::monitoring` uses Puppet virtual resources (`@package`, `@service`, `@cron`) that are only realized in production via `if $facts['environment'] == 'production'`. **Mitigation:** Replace with Ansible `when: ansible_environment == 'production'` conditionals on the relevant tasks. The Prometheus node-exporter and pushgateway tasks should be in a dedicated `monitoring` role applied only to production inventory groups.

- **Custom Facter facts**: Three custom Ruby Facter facts are used: `haproxy_version` (reads `haproxy -v` output), `redis_role` (reads replica config file), and `base_utils_info` (purpose inferred from name). These drive conditional logic in manifests. **Mitigation:** Replace with Ansible `setup` module facts where possible, or use `ansible.builtin.command`/`stat` tasks to gather equivalent information and register results as variables. The `redis_role` fact is the most critical — it determines primary vs. replica configuration.

- **Systemd daemon-reload orchestration**: `profile_app_stack::service` uses `refreshonly: true` on `systemctl daemon-reload` triggered by the unit file resource. Ansible's `ansible.builtin.systemd` module handles `daemon_reload: true` natively, but the ordering must be explicit in the task sequence.

- **Alembic migration idempotency**: The `run_db_migrations` exec uses `refreshonly: true` (only runs when the `vcsrepo` resource changes) and `onlyif` guards checking for `alembic.ini` and `migrations/env.py`. In Ansible, this must be replicated with `changed_when`, `when`, and handler notification patterns to avoid running migrations on every playbook run.

- **Duplicate module paths**: Three modules exist in both `modules/` and `site/modules/linux/` (`profile_app_stack`, `profile_haproxy`, `profile_redis_cluster`). The `site/modules/linux/` versions are authoritative (they appear first in `modulepath`). The `modules/` copies appear to be older versions — `profile_haproxy` in `modules/` lacks `discover.pp` and has a narrower OS support matrix. **Mitigation:** Migrate only from the `site/modules/linux/` versions. The `modules/` copies should be archived and not migrated.

- **`profile::base::base` SSH hardening gap**: The global `data/common.yaml` declares SSH hardening parameters (`permit_root_login`, `client_alive_interval`) but no Puppet class in the reviewed code consumes them. This suggests either a missing module or dead configuration data. **Mitigation:** Audit whether an SSH hardening class exists outside this repo before migrating; if not, implement it explicitly in the Ansible base role.

### Migration Order

The following order minimizes risk by starting with the lowest-complexity, highest-reuse module and ending with the most complex inter-node coordination patterns:

1. **`base_utils` + `profile::base::base`** — No external service dependencies, pure OS configuration (packages, MOTD, NTP, syslog). Establishes the Ansible role skeleton, `group_vars` structure, and Vault setup. The Bolt tasks/plans become Ansible ad-hoc commands and a `rolling_restart` playbook. Delivers immediate value as the foundation for all subsequent roles.

2. **`profile_app_stack`** — Self-contained single-node workload with well-defined inputs (Git repo, PostgreSQL, systemd). No inter-node coordination. Validates the Vault secret migration (db_password, secret_key), the `ansible.builtin.git` replacement for `vcsrepo`, and the Jinja2 template for `.env`. The monitoring sub-tasks (Prometheus) can be deferred to a later iteration.

3. **`profile_redis_cluster`** — Moderate complexity. Single-node Redis installation is straightforward; the PuppetDB-based cluster discovery and `redis_role` fact require the most design work. Migrate as a static-inventory single-node role first, then extend to multi-node with explicit primary/replica group assignments in the Ansible inventory.

4. **`profile_haproxy`** — Highest complexity due to the deep Hiera hierarchy, deep-merge backend composition, exported resources for dynamic backend discovery, and SSL configuration. Migrate the static Hiera-driven configuration first (using `group_vars` to replicate the datacenter/cluster/environment layers), then address dynamic backend discovery as a separate workstream once the inventory strategy is finalized.

### Assumptions

1. **Authoritative module versions**: It is assumed that `site/modules/linux/` modules are the production-authoritative versions and that the identically-named modules under `modules/` are older copies kept for reference or Vagrant testing. The migration plan is based exclusively on the `site/modules/linux/` variants.

2. **eyaml private key availability**: It is assumed the PKCS7 private key at `/etc/puppetlabs/puppet/eyaml/private_key.pkcs7.pem` is accessible to the migration team for decrypting existing secrets. If the key has been rotated or is held by a separate security team, secret extraction will require a separate process.

3. **Redis password override**: The `redis_password: 'CHANGEME'` default in `profile_redis_cluster` is assumed to be overridden by a node-level Hiera file not present in this repository (e.g., `data/nodes/<certname>.yaml`). If no override exists, production Redis nodes are running with the insecure default and this must be treated as a security incident, not just a migration task.

4. **No live PuppetDB dependency in Ansible**: The migration assumes that the dynamic node discovery currently performed by PuppetDB queries will be replaced by static Ansible inventory groups or a dynamic inventory plugin. The exact inventory source (CMDB, cloud provider API, static files) is not specified in this repository and must be decided by the platform team.

5. **SSL certificate pre-placement**: The Puppet code does not provision SSL certificates — it only references paths. It is assumed certificates are deployed by an out-of-band process (e.g., a PKI system, Let's Encrypt, or manual placement). The Ansible migration must either replicate this assumption or introduce explicit certificate management tasks.

6. **Single datacenter scope**: Only one datacenter (`dc1_fra`, Frankfurt) is represented in the Hiera data. It is assumed this is the only active datacenter and that the migration does not need to account for additional datacenter hierarchies beyond what is present.

7. **Ubuntu 24.04 as primary target**: The Vagrant and test infrastructure targets Ubuntu 24.04. The `site/modules/linux/` metadata declares broader OS support (RHEL 8/9, Debian 11/12, Ubuntu 22.04/24.04), but no RHEL- or Debian-specific configuration logic was found beyond package name variants in `base_utils`. It is assumed Ubuntu 24.04 is the primary migration target, with multi-distro support as a follow-on effort.

8. **Bolt plans are operational, not provisioning**: The `base_utils` Bolt plans (`health_check`, `rolling_restart`) are assumed to be operational runbooks rather than provisioning steps. They will be migrated to Ansible playbooks but are not on the critical path for infrastructure provisioning.

9. **`profile::base::base` SSH hardening**: The SSH parameters in `data/common.yaml` (`ssh::permit_root_login`, `ssh::client_alive_interval`) are assumed to be consumed by a module not present in this repository. If no such module exists, these represent unimplemented configuration intent that should be explicitly implemented in the Ansible base role.

10. **No Puppet Server / agent infrastructure migration**: This plan covers only the migration of Puppet manifests, modules, and data to Ansible playbooks and roles. The decommissioning of the Puppet Server, PuppetDB, and agent infrastructure is assumed to be a separate workstream managed by the operations team.
